\subsection{SQL-based RAG}
Relational databases have long been the default for storing structured data. Recent work starts applying them to agentic RAG and agent memory. SAG \cite{wu_sag_2026} argues that naive RAG yields shallow retrieval, while graph-based RAG is slow, costly, and hard to update. They therefore use SQL as the backbone of RAG. Documents are stored as an event-entity incidence table. At query time, an LLM extracts entities from the query, and a JOIN retrieves events sharing these entities as seeds. A reverse JOIN then collects the entities attached to these seed events, and a further JOIN brings in previously unseen events incident to them. The expanded event set is passed back to the LLM, which selects the evidence and maps it to the original chunks. There are also other works that frame agent memories as databases like \cite{orogat_agent_2026}.

\subsection{Skill Training} 

Training model weights, especially with reinforcement learning (RL), is expensive, slow, and not portable (you would need to host and run this specific model, which might perform poorly on general tasks). Many recent works began to train the agent's Skill document instead of model weights, which can be seen as a form of prompt optimization.

\textbf{Training-free GRPO}~\cite{_251008191_} uses an approach similar to the original gradient-based GRPO~\cite{shao_deepseekmath_2024}. An initial experience and a policy model are used to roll out a batch of traces, and another LLM computes the semantic advantage of each rollout, analogous to the numeric advantage in the original GRPO. These semantic advantages are used to update the experience. \textbf{Trace2Skill}~\cite{ni_trace2skill_2026} uses parallel rollouts in batches to collect many traces and generate patches for successful and failed traces. These patches are then merged into the final Skill in sequence. Compared to training-free GRPO, this can be seen as a form of offline reinforcement learning. \textbf{SkillOpt}~\cite{yang_skillopt_2026} treats Skill optimization similarly to gradient descent, where the editing budget is analogous to the learning rate, the gradient direction is analogous to the editing direction, etc. It also learns a meta-skill to track what kind of edit is helpful using a held-out validation set. \textbf{SkillCAT}~\cite{chen_skillcat_2026} uses DPO-style training. It samples two paired rollouts: a successful one ($r^+$) and a failed one ($r^-$). It then analyzes the two traces, finds the point where they diverge, and generates a patch contrastively. The patch is then verified to see whether it helps the agent, similar to the gate in SkillOpt, and is merged if it turns a failure into a success or maintains a success. However, in many cases, the two traces are completely independent (with no shared prefix beyond the prompt), or the divergence point does not affect the result.


\section{VideoSQL}
\subsection{Indexing}
For a fair comparison with our baseline MAGIC-Video~\cite{li_bridging_2026}, we re-used their index.  We convert their index from a graph data structure into a relational database by constructing a table for each node type, and use an outer key as an edge. We also formulated the topic chain and event chain into tables. This yields major tables of episode captions, semantic triplets, entities, and topic and event chains. The detailed schema of our database is in the appendix and readers can also refer to the MAGIC-Video paper for details of these indices. 

\subsection{SQL-based queries}
MAGIC-Video uses Personalized Page Rank (PPR) to retrieve nodes in the graph by a query generated by the LLM, with which the agent has no control over the relations between nodes. We still keep a simple semantic search tool for the model to search all text and images using embeddings. For example, if the agent wants to find who ate the apple yesterday at noon, it likely issues a query like "person ate apple yesterday noon" and hopes the PPR returns relevant nodes. Instead, we formulate this using a relational database. Given the same index structure as MAGIC-Video, the agent can write a SQL query like in \cref{lst:sql-example}. Even though searches like this could be replaced with dedicated tools like \texttt{search\_semantic(object="apple", time\_s=time\_s, time\_end=time\_end)}, using SQL as an interface provides a unified interface with more freedom and does not require specific design for each case (for example, if we need to search "the person who ate the apple that is not Luke", we would need to re-design the tool signature). It can also be seen as a form of Programmatic Tool Calling. Such an interface can also handle complex queries using advanced SQL features like JOIN, GROUP BY, and sub-queries when needed. 

Our work differs from SAG \cite{wu_sag_2026} in that the LLM controls the SQL generation and it can use all SQL features, unlike SAG which only used JOIN as a way to expand the seed nodes. 

\begin{lstlisting}[language=SQL, caption={An example SQL query for finding who ate the apple within a given time window.}, label={lst:sql-example}]
SELECT *
FROM semantic_triples
WHERE predicate IN ('eat', 'eats', 'ate', 'eating')
  AND object IN ('apple', 'the apple', 'an apple')
  AND snapshot_s >= $start_s
  AND snapshot_s < $end_s;
\end{lstlisting}

\section{Evaluations}
\subsection{Datasets}
We used the two most popular ULVU datasets in the paper: EgoLifeQA~\cite{yang_egolife_2026} and MM-Lifelong~\cite{chen_multimodal_2026}. EgoLifeQA uses multiple-choice questions (MCQ) while MM-Lifelong uses open QA. EgoLifeQA contains one week of recording in the same setting while MM-Lifelong has 3 different settings (day, week, and month), each with its own video. The MM-Lifelong week subset has the same video as EgoLifeQA. We argue that MCQ does not reflect realistic usage since most questions asked by users in the real world are open. Additionally, agents can brute-force verify each option to artificially boost accuracy. We therefore reformulated EgoLifeQA into open QA questions (Open-EgoLifeQA) similar to MM-Lifelong and evaluated both using LLM-as-judge for semantic comparison between the ground-truth and predicted answers. To compare with prior work, we used the Jack view from EgoLifeQA. We evaluated our untrained VideoSQL on both Open-EgoLifeQA and the MM-Lifelong validation set. 

To train the VideoSQL Skill, we need to select an independent training set. Ego-R1 Data~\cite{tian_egor1_2025} is a training set built on top of EgoLifeQA and the authors of Ego-R1 trained their method on this dataset and then tested on EgoLifeQA. MM-Lifelong also has a training split as well. However, these training sets overlap with their corresponding validation/testing sets at the video level. While no questions are leaked, we argue that sharing videos could still inflate performance, or at least fail to test the model's ability for cross-domain generalization. To address this, we trained our Skill on EgoLifeQA and tested it on the more challenging MM-Lifelong (for context, MAGIC-Video reached 67.6 on EgoLifeQA but only 24.5 on MM-Lifelong). 


\subsection{Baselines}
We re-ran the MAGIC-Video \cite{li_bridging_2026} as our training-free baseline as we share the same indices. Both MAGIC-Video and our method used Qwen-3.8-27B~\cite{qwen38} as the policy model and Qwen3-VL-Embedding-8B \cite{li_qwen3vlembedding_2026} as embedding model. We also compared with a couple other baselines directly with their reported numbers. We also selected Trace2Skill \cite{ni_trace2skill_2026} and SkillOpt \cite{yang_skillopt_2026} for our skill-trained variant, both built on top of the same VideoSQL harness.
